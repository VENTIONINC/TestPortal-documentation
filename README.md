# Test Portal documentation

English public product documentation for Test Portal, built with Docusaurus Classic 3.10.2, TypeScript, React and MDX. The foundation covers TP-8, TP-9 and TP-15 checks. Public guides for TP-10–TP-13 cover onboarding/CLI, framework/CI integrations, REST/MCP and UI troubleshooting. TP-14 adds generated LLM exports; TP-16/TP-17 preparation covers deployment and contribution guidance. Per-ticket acceptance and remaining gates are in [FINAL-ACCEPTANCE.md](FINAL-ACCEPTANCE.md).

The configured future site is <https://ventioninc.github.io/TestPortal-documentation/>. Publication has not been enabled or verified.

## Local setup

Use Node.js 22 (see `.nvmrc`) and npm. Node 24 is also supported by this project.

```bash
nvm use
npm ci
npm start -- --no-open
```

Open <http://localhost:3000/TestPortal-documentation/>. Preserve the project base path when testing links and assets.

```bash
npm run build
npm run serve -- --no-open
```

Search indexes are generated by production builds. Test search with `serve`; development mode alone is not search acceptance. The local search plugin does not require hosted search credentials.

## Add or update documentation

1. Review the current source default branches and record the inspected commits and evidence in [MIGRATION.md](MIGRATION.md).
2. Verify public support, behavior and examples against implementation. Flag unresolved claims instead of inventing behavior. Review public suitability before adding content; never copy whole source documentation directories.
3. Add Markdown/MDX under `docs/`. Each page needs `title`, `description`, a unique explicit `slug`, and a descriptive H1. Use a fenced language for executable examples and valid JSON/YAML rather than ellipses presented as executable data.
4. Add the reviewed page and commit-permalink evidence to `public-content.json`. Review public assets and site source changes in the same PR. Draft/unlisted content is not approved public input; keep research outside the publication directories.
5. Sidebar entries are generated within each section by `sidebars.ts`. Update `docusaurus.config.ts` for navbar destinations. Use Docusaurus links and Markdown file links so paths work below the configured base URL. Keep the homepage first-report tutorial link current. For a new top-level section, add its export category in `scripts/llms.mjs`.
6. Run the shared validation command and submit a focused PR to `develop` (or `main` when explicitly requested). Keep acceptance separate for tickets sharing a PR.

`src/pages/index.tsx` is the homepage; `src/css` holds theme adjustments; `src/components` is available for small shared components; `static/img` is reserved for explicitly reviewed assets. Everything in `static` is copied publicly, so do not store private or unpublished files there.

## Validation

```bash
npm run validate
```

This runs:

- `lint:md`: Markdown headings, fences, whitespace, empty links and formatting. Generated directories are excluded.
- `check:docs`: required page metadata, unique routes, explicit public-input list, commit evidence, JSON/YAML examples, shell syntax, CLI flag/provider compatibility and concrete multipart API examples. Workflow YAML and referenced integration environment variables are also checked.
- `typecheck`: TypeScript for the configuration and React source.
- `test:checks`: positive and negative fixtures for validation failures.
- `build`: production Docusaurus build with strict links, anchors, images and duplicate routes.
- `check:artifacts`: required pages, sitemap, local search index, base-path-aware internal links/assets/anchors, and public-content scanning of built output.
- `check:llms`: exact approved-page coverage and content, clean Markdown, resolved absolute URLs, target/anchor existence, source exclusions and unexpected export detection.
- `check:llms-stability`: rebuilds production output, revalidates exports and compares SHA-256 hashes of all 27 LLM artifacts. This runs in PR and deployment CI.

CLI compatibility checks use the audited command snapshot in `scripts/cli-contract.json`; update it when adopting a newer CLI baseline. This catches syntax drift relative to that snapshot, not runtime integration failures. Shell snippets are syntax-checked with Bash and never executed. JavaScript/TypeScript examples are compiled by MDX as display content, not run as application code; verify their runtime behavior separately.

Public checks in `scripts/checks.mjs` detect recognizable tokens, private keys, credential literals, local paths, internal domains and excluded source references. New publication inputs require an explicit manifest change. The checks report rule names rather than credential values. Binary image assets currently require extending the reviewed validation policy; no product screenshots are bundled. Automated scanning does not establish confidentiality or replace human public-content review.

External URLs are not fetched in blocking CI. Review them separately with bounded timeouts/retries when needed. The PR workflow has `contents: read`, disables persisted checkout credentials, uses pinned actions, and has no deployment or production-instance access.

## Content verification

[CONTENT-VERIFICATION.md](CONTENT-VERIFICATION.md) records per-ticket acceptance, audited source commits, generated-report conversion checks and remaining external gates. It is repository bookkeeping, outside public site inputs. The normalizer regression checks execute the actual code blocks in the Jest/Cypress guides and reject lost tests.

For an optional local runtime check, supply an independently built CLI at the audited commit and a directory containing the generated report fixtures described in that record:

```bash
node scripts/verify-cli-examples.mjs "$TEST_PORTAL_AUDITED_CLI" "$TEST_PORTAL_EXAMPLE_REPORTS"
```

This check uses a local HTTP mock, never a production instance; it requires permission to bind a loopback port. The regular `npm run validate` command does not require source checkouts, registry credentials or a running Test Portal instance.

## Separate live verification

Before approving full guides, use a disposable project on an authorized test instance:

1. Confirm the published CLI package can be installed with the documented registry access.
2. Generate real Playwright/Jest/Cypress reports and check converted CTRF output, including retries and nested suites where applicable.
3. Submit sanitized reports with the documented credentials; inspect HTTP/upload outcomes and verify the matching project, execution and results in the UI. Do not infer success from CLI exit status alone.
4. Check invalid credentials/payloads and observed error messages. Keep credentials out of logs, screenshots and commits.
5. Connect a compatible MCP client with a dedicated token; inspect discovered tools and verify only the documented public operations.
6. Verify desktop/mobile navigation, both themes, keyboard access and production search.

These steps require appropriate access and are not satisfied by static CI. Findings and outstanding acceptance belong in the inventory/PR.

## Dependency audit

The foundation pins Docusaurus 3.10.2 and uses the npm lockfile. Targeted overrides select Tinypool 2.1.2 and serialize-javascript 7.1.2 to address the worker-option and serialization advisories; validate both development startup and production builds when changing those overrides.

The 2026-10-20 audit still reports 53 dependency findings (30 high, 20 moderate, 3 low; zero critical). These counts include dependent packages, not 53 independent defects. Remaining underlying advisories concern braces, KaTeX, postcss-selector-parser, smol-toml, sprintf-js and uuid. In particular, the installed latest braces release remains flagged for deeply nested glob denial of service. A clean audit is not claimed; review upstream fixes before enabling publication and keep CI isolated from production credentials. Do not apply force-downgrades that abandon the selected Docusaurus release.

Advisory references: [Tinypool](https://github.com/advisories/GHSA-85c8-ppgw-ccpr), [serialize-javascript](https://github.com/advisories/GHSA-5c6j-r48x-rmvq), [braces](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm).

## LLM exports

Every `npm run build` runs `scripts/llms-plugin.mjs`. It joins the 25 explicitly approved `public-content.json` entries to Docusaurus's resolved document metadata. Explicit slugs and `site-settings.json` determine output routes; directory names do not substitute for routes. No separate handwritten version of a page is maintained.

The build produces `build/llms.txt`, `build/llms-full.txt`, and `build/docs/<resolved-slug>.md`. For example, the integration hub exports as `build/docs/integrations.md`; source links to `integrations/index.md` become absolute published HTML URLs. `llms.txt` links to Markdown exports by category. The combined file uses a fixed category/slug order, original headings and intact code fences. Repository bookkeeping stays outside the exports, site and search.

Imports outside code fences are removed. Components, expressions and raw HTML with potentially hidden content cause a build failure: use ordinary Markdown instead of silently losing rendered information. Relative document links must resolve to approved source pages; export validation checks their published targets and anchors. New assets or syntax require a deliberate extension of this small generator and its tests.

The requested `docusaurus-plugin-llms` 0.6.1 was evaluated with Docusaurus 3.10.2. Its peer range is compatible and it generated all 25 exports, but it retained source-relative `index.md` links despite exporting hub pages under their slugs. Those links broke in per-page and combined output. The minimal local generator fixes this and enforces the existing approved-source manifest without extra dependencies. See the evidence and regression cases in [FINAL-ACCEPTANCE.md](FINAL-ACCEPTANCE.md).

## Deployment and public verification

The reviewable `.github/workflows/deploy.yml` runs only on pushes to `main`. Its build job installs locked dependencies and runs the complete shared validation, including repeated export builds, before uploading the entire `build` directory with the official Pages artifact action. The dependent deploy job uses `actions/deploy-pages`, the `github-pages` environment, and job-scoped `pages: write` / `id-token: write`. Other jobs have only `contents: read`. Concurrency serializes deployments; PR builds never publish.

**Publication approval is still required before promoting this workflow to `main` or enabling Pages.** An authorized maintainer/administrator must confirm repository access and visibility, select GitHub Actions as the Pages source, configure the `github-pages` environment/reviewer policy, and confirm applicable protected-branch requirements. These settings are not changed by the PR. There is no custom domain or manual deploy command.

The configured URL is <https://ventioninc.github.io/TestPortal-documentation/>. The merged foundation selected this actual repository name; the original ticket URL ending in `/TestPortal-docs/` is superseded. Keep `site-settings.json`, repository links, validators and rollout records consistent if an approved rename occurs.

After an authorized deployment, the workflow runs `npm run check:live`. The bounded HTTP smoke check verifies every approved HTML page and Markdown export, both LLM files, sitemap coverage, navigation and referenced CSS/JavaScript responses under the project path, with three attempts and 10-second request timeouts. It fails on missing/empty/wrong content and incorrect base paths. It cannot establish visual layout or execute application JavaScript; perform the separate desktop/mobile, themes and production-search browser checks. A failed smoke job reports a failed release check but does not automatically roll back an already deployed site.

For a local server mounted at the configured base path, the same smoke procedure can be exercised without publication:

```bash
DOCS_SMOKE_ORIGIN=http://localhost:3000 npm run check:live
```

Record local results separately from public HTTP evidence. After the live site is verified, obtain explicit approval for narrow Documentation links in the client, backend and CLI READMEs. Each repository needs its own branch/PR; preserve existing material. No ecosystem README edits are part of this documentation branch.
