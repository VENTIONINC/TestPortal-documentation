# Contributing

Submit documentation changes through pull requests to `develop`. Releases are promoted from `develop` to `main` after review and passing checks.

## Source accuracy and public content

Verify product behavior against the current default branches of [TestPortal-client](https://github.com/VENTIONINC/TestPortal-client), [TestPortal-backend](https://github.com/VENTIONINC/TestPortal-backend) and [TestPortal-cli](https://github.com/VENTIONINC/TestPortal-cli). Source code and maintained schemas take precedence over outdated examples.

`public-content.json` is the reviewed publication manifest. It records each public page, explicit slug and commit-permalink source references. Update those references when adopting newer behavior. Keep `scripts/cli-contract.json` aligned with the CLI version used by the guides and validation checks. Commit references identify a source baseline; they do not prove that a feature is available on a deployed instance.

Select public material explicitly. Do not copy whole source documentation directories. Exclude internal specifications, roadmaps, infrastructure details, security implementation details, unreleased features and unrelated development/release instructions. Sanitize examples and screenshots; never publish credentials or private instance data. Everything under `static/` is copied to the public build.

## Add or update a page

1. Add ordinary Markdown under `docs/` with `title`, `description`, a unique explicit `slug` and a descriptive H1. Draft/unlisted pages cannot be approved publication inputs.
2. Check commands, defaults, supported formats, API contracts and UI steps against the owning implementation. Distinguish placeholders from real defaults and credentials from one another.
3. Add the reviewed page and source references to `public-content.json`. Review assets and site source changes in the same PR.
4. Sidebar entries are generated by `sidebars.ts`. Update `docusaurus.config.ts` for navbar destinations and keep the homepage tutorial link current. Add a category in `scripts/llms.mjs` for a new top-level section.
5. Use relative Markdown file links for documentation pages. The build resolves them to the configured project path, including explicit slugs.
6. Run `npm run validate`, inspect the production preview and submit a focused PR.

The homepage is `src/pages/index.tsx`; theme styling is in `src/css/`. Small shared components belong in `src/components/`; reviewed assets belong in `static/img/`. Public article content must remain readable in generated Markdown: the export generator removes imports outside code fences and rejects React components, expressions and raw HTML instead of dropping their content.

## Validation coverage

`npm run validate` checks Markdown formatting, metadata, public-input coverage, source references, JSON/YAML/shell examples, CLI contracts, TypeScript, validation regressions, production links/anchors/assets, sitemap/search output, complete LLM exports and byte stability across repeated production builds.

Shell snippets are syntax-checked, not executed. JavaScript/TypeScript display examples are not application runtime tests. CLI checks use the recorded contract snapshot, not a live registry or server. External links are not fetched in blocking CI; check them separately with bounded timeouts/retries. Public-content scanning supplements human review and reports rule names without printing matched credentials. Binary assets require a deliberate extension of the reviewed validation policy.

## Verify CLI examples locally

Build the CLI at the commit recorded in `scripts/cli-contract.json`, using its locked dependencies in an isolated checkout, then point `TEST_PORTAL_AUDITED_CLI` at `dist/cli.js`. Do not use an unrelated dirty feature checkout as the behavior baseline.

In a separate fixture project, install `@playwright/test@1.58.2`, `jest@29.7.0`, `mocha@11.7.5` and `mochawesome@7.1.4`. Use a fresh `reports` directory. The following is a sufficient Playwright test (save under the configured test directory):

```javascript
const {test, expect} = require('@playwright/test');
test.describe('nested', () => {
  test('passes', () => expect(1).toBe(1));
  test('fails', () => expect(1).toBe(2));
});
```

Generate `reports/playwright.json` using the JSON reporter, with retries 1. For Jest, make the equivalent two tests using its global `describe`, `test` and `expect`; use `--runInBand --json --outputFile=reports/jest.json`. For Mochawesome, use nested Mocha suites with `assert.equal(1, 1)`, `assert.equal(1, 2)` and one `it.skip`, then save JSON using `--reporter mochawesome --reporter-options reportDir=reports,reportFilename=cypress,html=false,json=true`. Run each producer separately, retaining its expected nonzero test outcome. Set `TEST_PORTAL_EXAMPLE_REPORTS` to this reports directory.

From this documentation repository:

```bash
node scripts/verify-cli-examples.mjs "$TEST_PORTAL_AUDITED_CLI" "$TEST_PORTAL_EXAMPLE_REPORTS"
```

The script extracts the tutorial sample and exact normalizer code blocks, converts the real producer reports, checks counts/names/statuses/retries, then verifies the webhook failure caveat against a local HTTP mock. It never contacts a real instance. Normalizer regressions also run in regular CI using small synthetic inputs, including negative count/state cases.

For MCP reproduction, install SDK 1.29.0 in an isolated directory, copy the page's `connect.mjs`, and configure a local authenticated Streamable HTTP mock with a registered `testportal-check-status` tool. Assert the Bearer header on initialization and subsequent requests; verify tools discovery, status content and connection close. Use a disposable Test Portal project to verify actual server behavior.

## Verify product workflows

Use an authorized disposable project and sanitized data when changing integration instructions:

1. Install the documented CLI package from its configured registry; check executable, help and version behavior.
2. Generate actual framework reports. Inspect normalized and converted counts, names, statuses and retries, including nested suites and multiple Cypress specs when applicable.
3. Upload a report and require the documented HTTP status, response fields and processed count. Verify the same execution and results in the UI with the correct project/date and cleared filters. A CLI exit status alone does not establish upload success.
4. Check invalid credentials and malformed payloads without logging tokens or full authorization headers. Avoid automatic retries after uncertain uploads that could duplicate data.
5. Exercise the CI example with an intentional failing test: preserve test failure, retain artifacts and check the upload independently.
6. Connect a compatible MCP client with a dedicated token. Compare discovered tools and documented inputs; exercise writes only on disposable data and inspect tool errors independently of HTTP status.

Record relevant results and limitations in the PR. Static builds, mocks and source inspection do not establish released-package availability or live product behavior.

## Review the built website

Run `npm run build` and `npm run serve -- --no-open`. Check desktop/mobile navigation, both themes, keyboard access, the first-report link and production search. Development mode does not generate the production search index.

After deployment, `npm run check:live` verifies HTTP page/export content, sitemap coverage, navigation and linked CSS/JavaScript. It does not execute browser JavaScript or establish visual correctness. Inspect the deployed site in a browser as well.

## Dependency maintenance

Use the npm lockfile and run `npm audit` when updating dependencies. Review remaining advisories rather than treating a successful build as a clean security audit. Targeted overrides in `package.json` must be checked with both development startup and production builds when changed; avoid force-downgrades that abandon the selected Docusaurus release.
